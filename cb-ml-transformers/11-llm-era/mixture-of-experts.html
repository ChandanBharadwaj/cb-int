Mixture of Experts & the Modern Decoder

The model card says "8×7B — 46.7B parameters, 12.9B active." Until now, that sentence had a contradiction in it: how can a model both have 47 billion parameters and not have them? This page resolves it — and while we're inside a modern decoder anyway, it closes the course's architecture thread by reading a real flagship config file line by line, every line mapping to a page you've already done.

Specialize the FFN, route per token

Recall where a transformer keeps its bulk: M5.5 showed the FFN holds roughly two-thirds of every block's parameters — and hinted it acts as key–value memory, where patterns get recognized and facts get written back. Mixture of Experts takes that observation literally: if the FFN is the memory, why should every token consult all of it? MoE replaces each block's single FFN with N parallel FFNs — "experts" — plus a tiny router: a linear layer that scores the experts for each token, picks the top-k (typically 2 of 8), and sends the token through only those. Attention is untouched — every token still attends over the full sequence with shared, dense attention weights (M5.3–M5.4). Only the memory-lookup half of the block got carved into specialists.

y  =  Σi ∈ top-2 gi · Ei(x),    g = softmax(Wrouter · x)
In plain words: a tiny linear layer scores all the experts for this token; only the two winners actually run; their outputs mix, weighted by the scores. Everything else stays a normal transformer block.

The router: a learned traffic cop with problems

The router trains by ordinary backprop — gradients flow through the gate weights of whichever experts ran — and that creates a famous instability: rich-get-richer collapse. An expert that starts marginally better gets routed more tokens, so it trains more, so it gets better, so it gets routed more… until a couple of experts absorb all traffic and the rest sit idle — a dense model dragging dead weight. The standard fix is a load-balancing auxiliary loss: a small penalty on uneven expert traffic within each batch, nudging the router to spread tokens without dictating assignments. Training systems also set a capacity factor — a per-expert token budget per batch (needed to make batched matmuls rectangular); tokens overflowing a popular expert get dropped — skipped past the layer through the residual connection (M5.5's highway earning its keep in a way nobody advertises).

Params ≠ FLOPs anymore

MoE breaks a rule the whole course has quietly relied on: that parameter count predicts both memory and compute. Now they split. Memory bills the total — all 46.7B parameters must sit in VRAM, because any token might route anywhere (M7.2's arithmetic runs on the big number). Compute bills the active — each token touches 12.9B, so per-token FLOPs and decode speed behave like a ~13B model (M7.5's economics run on the small one). That asymmetry also explains MoE's serving personality: at high batch sizes it shines — many tokens spread across all experts, every loaded parameter earns its keep. At batch 1 it disappoints — you paid the full memory bill, decode is bandwidth-bound (M7.1), and the weights you must stream per token still skew large for the quality you get. And at scale the experts get sharded across GPUs, so every MoE layer pays an all-to-all communication tax shipping tokens to their experts and back (M7.3's lesson: renting the fleet's memory always charges in communication).

active ≈ attention + shared  +  k · paramsexpert   (Mixtral: ≈ 12.9B of 46.7B with k = 2 of 8)
In plain words: per token you pay for attention (always dense), the shared plumbing, and just k experts' worth of FFN. The other N−k experts cost memory, not compute.
Real numbers

Mixtral 8×7B: 46.7B total, 12.9B active — matched or beat Llama-2-70B on most benchmarks at roughly 6× the decode speed. DeepSeek-V3: 671B total, 37B active, with 256 fine-grained experts routed top-8. And GPT-4 is widely reported to be an MoE — a claim never officially confirmed, worth labeling as such when you repeat it.

What experts actually learn

The name oversells it. Analyses of trained MoEs mostly do not find "the biology expert" and "the law expert" — routing decisions correlate with token-level features: punctuation, numbers, code tokens, whitespace patterns, particular syntactic positions. The router operates on a single token's hidden state, so it specializes on what that state exposes — surface and syntax more than topic. Same honesty M5.4 demanded for attention heads: real, measurable specialization, rarely the human-shaped story the diagram suggests. The engineering win doesn't care — quality per FLOP improves whether or not the experts' division of labor flatters our intuitions.

The rest of the modern decoder, in one config

Mixtral's config.json is the course's final exam, and you can now pass it on sight — the same ritual as M5.6's encoder config, eight pages of ideas later: 

{
  "hidden_size": 4096,              // the residual stream            (5.5)
  "num_hidden_layers": 32,          // rounds of message passing      (5.6)
  "num_attention_heads": 32,        // query heads                    (5.4)
  "num_key_value_heads": 8,         // GQA: 4 queries share each KV   (5.4, 11.2)
  "rope_theta": 1000000.0,          // RoPE base — the long-ctx knob  (5.2, 11.2)
  "rms_norm_eps": 1e-05,            // RMSNorm, pre-norm placement    (5.5)
  "hidden_act": "silu",             // SwiGLU-family FFN activation   (5.5)
  "num_local_experts": 8,           // the eight FFNs per layer       (this page)
  "num_experts_per_tok": 2,         // top-2 routing                  (this page)
  "vocab_size": 32000               // SentencePiece BPE              (5.1)
}

Every line is a page. RMSNorm is M5.5's LayerNorm minus the mean-centering; SwiGLU is the FFN with a learned gate multiplying the expanded activations (a few percent better per FLOP — enough that everyone switched); RoPE and GQA you've already met. A "modern decoder" is not a new architecture — it's the 2017 transformer with five well-chosen substitutions, and now one of them is yours too.

Connect it to your stack

This is why "flagship quality at mini prices" keeps happening on pricing pages: an MoE serves quality tied to total parameters at a per-token compute cost tied to active ones. It's also why two dashboards disagree about the same model — VRAM usage tells the 47B story (M7.2), tokens-per-second tells the 13B story (M7.5). Neither is lying; they're billing different columns.

Build it: a router in numpy

Make 8 tiny two-layer MLPs (the experts) and one 8-way linear router. For a batch of random "tokens": softmax the router logits, mask to top-2, run only the chosen experts, blend by gate weight. Count multiply-adds vs running all 8 — you'll see the 2/8 compute ratio directly. Then train on a toy task and print per-expert traffic with and without a load-balance penalty (penalty = var(traffic) works): watch collapse happen, then watch the leash prevent it.

If you remember one thing

MoE splits the one number you used to trust into two: total parameters (what you store — memory, VRAM, download size) and active parameters (what each token runs — FLOPs, latency, per-token cost). A learned router picks top-k experts per token; a load-balancing loss keeps it from collapsing onto favorites; attention stays dense throughout. When a model card says "8×7B, 13B active," it is quoting both bills — and when someone asks whether a 47B MoE is "bigger" than a 13B dense model, you now know the only honest answer: bigger in memory and quality, the same size in compute. One number was never going to be enough.

Interview questions

Total vs active parameters — which predicts memory, which latency, which quality?

Memory: total — all experts must be resident in VRAM because any token may route to any of them, so a 47B-total MoE needs ~47B parameters' worth of storage (M7.2's math on the big number). Latency and per-token cost: active — each token executes attention plus k experts, so FLOPs and decode speed track ~13B (with a caveat: batch-1 decode is bandwidth-bound, and the weights streamed per step depend on which experts fire across layers, so small-batch latency sits somewhat worse than a true 13B dense model). Quality: between the two, empirically closer to what the total buys — Mixtral's 46.7B/12.9B matching Llama-2-70B while decoding ~6× faster is the canonical data point. Interviewers want the split stated crisply; bonus points for noting the two dashboards (VRAM vs tokens/s) tell different, equally true stories.

Why does MoE need a load-balancing loss, and what happens without it?

Because routing is trained by the same gradients as everything else, and that closes a positive feedback loop: an expert that starts slightly better receives more tokens, therefore more gradient updates, therefore improves faster, therefore wins even more routing. Left alone, this rich-get-richer dynamic collapses traffic onto one or two experts — the rest become dead parameters you still pay VRAM for, and the model behaves like a smaller dense network dragging anchors. The load-balancing auxiliary loss adds a small penalty on uneven per-batch expert traffic, keeping all experts in the training signal without hard-assigning tokens. Related machinery: capacity factors cap tokens per expert per batch (for rectangular batched matmuls), and overflow tokens get dropped — passed through the residual connection, skipping the layer entirely.

Why put the experts in the FFN but keep attention dense?

Three reasons. Capacity: the FFN holds roughly two-thirds of each block's parameters (M5.5), so expertizing it multiplies capacity where capacity lives — expertizing attention would fragment a smaller pool. Function: the FFN acts as per-token key–value memory (pattern lookup and fact storage), which decomposes naturally into specialists, while attention's job is routing information between tokens — carving it up would fragment the very mechanism that lets tokens communicate, and per-token expert choice sits awkwardly with an operation defined across the whole sequence. Practicality: the FFN is applied independently per token, so routing different tokens to different experts is embarrassingly parallel; sparse per-token attention variants exist in research but add complexity for less headroom. So: specialize the memory, share the switchboard.

Why does MoE shine at high batch sizes but disappoint at batch 1?

At high batch, many tokens per step spread across all experts, so every parameter you're holding in VRAM does useful work, and per-token compute stays at the cheap "active" rate — you get big-model quality at small-model FLOPs with the memory bill amortized across users. At batch 1, decode is memory-bandwidth-bound (M7.1, M7.5): each step streams weights from VRAM, and with different experts firing across layers and steps you stream large amounts of a 47B model's weights to serve one user at 13B quality-per-FLOP. The memory cost is fully paid but barely amortized. Add expert parallelism at scale — experts sharded across GPUs means an all-to-all communication step per MoE layer — and single-stream latency takes a further tax. Consequence: MoE is a throughput architecture; providers love it, single-user local inference much less.

Is a 47B-total MoE "bigger" than a 13B dense model? Give the honest comparison.

Depends which bill you read. In storage and memory: yes — ~47B parameters to download and hold, VRAM sized accordingly. In per-token compute: no — ~13B active means FLOPs, decode speed, and marginal cost in the dense-13B class. In quality: usually meaningfully better than dense-13B — the router's conditional computation lets different tokens use different parameters, extracting more capability per FLOP — though typically short of a dense 47B trained on the same data. So the honest comparison is a triple: memory of a 47B, compute of a 13B, quality in between (usually much nearer the top). Anyone answering with a single number — in either direction — is reading only one column of a two-column bill, which is exactly the confusion the "8×7B" naming exploits.
